# Logging in git-hop

git-hop uses [charmbracelet/log](https://github.com/charmbracelet/log) for beautiful, structured logging with a Git-like style.

## Log Levels

git-hop logs at these levels:

- **debug** - Detailed diagnostic information, with `-V`
- **info** - General informational messages (default)
- **warn** - Warning messages
- **error** - Error messages
- **fatal** - Fatal errors that cause program exit

There is no log-level setting: `-V` (or `GIT_HOP_VERBOSE`) adds debug
output and `-q` drops everything but errors.

## Configuration

### Command-Line Flags

Use the `--verbose` or `-V` flag for debug-level logging:

```bash
git hop --verbose doctor
```

### Debug Switch

`GIT_HOP_VERBOSE` turns on `-V` for every run, the way `GIT_TRACE` does for
git. `true`, `yes` and `on` mean `-V`; `false`, `no`, `off` and an empty
value mean off (any case); a number is the `-V` count, so `2` is `-VV`.
Any other value prints a warning and counts as off. A `--verbose` on the
command line wins, so `--verbose=0` turns it off for one run:

```bash
export GIT_HOP_VERBOSE=1
git hop add feature-x              # debug lines, as with -V
git hop --verbose=0 add feature-y  # none
```

Use the `--quiet` or `-q` flag to suppress all output except errors:

```bash
git hop --quiet doctor
```

## Output Modes

git-hop supports different output modes:

### Human Mode (Default)

Clean, Git-like output for humans:

```
✓ Hopspace exists
error: failed to create worktree
```

### JSON Mode

`--json` (the same as `--format json`) switches the log lines on stderr to
JSON:

```json
{"level":"error","msg":"failed to create worktree"}
```

Every command that does something has a result, and `--json` also
renders it as one JSON document on stdout, with nothing else mixed in. A
command with no result (`upgrade`) refuses `--json` with exit 129 instead
of printing prose where JSON is expected:

```bash
git hop doctor --json
```

```json
[
  {
    "kind": "issue",
    "check": "hub",
    "subject": "feat/gone",
    "message": "worktree directory missing: /work/hub/hops/feat/gone"
  }
]
```

See [Structured Output](./09-reference#structured-output) for every
result shape and the other formats (`yaml`, `csv`, `text`).

### Porcelain Mode

Machine-readable, stable line format: one tab-separated record per line,
no header, columns in the order the result shape lists them:

```bash
git hop status --porcelain
```

Warnings and errors still print, on stderr, so they never break a parser
reading stdout. Hints and progress are dropped.

### Quiet Mode

Only report errors, like git's `-q`: progress, hints and warnings are
dropped, in every mode (`--porcelain -q` and `--json -q` included);
`error:` and `fatal:` lines always print:

```bash
git hop --quiet doctor
```

## Structured Logging (For Developers)

When developing git-hop commands, you can use structured logging with fields:

```go
import "hop.top/git/internal/output"

// Basic logging
output.Info("Creating worktree")
output.Debug("Verbose information")
output.Error("Operation failed: %s", err)

// Structured logging with fields
logger := output.WithFields(map[string]interface{}{
    "branch": "feature-x",
    "repo":   "my-repo",
})
logger.Info("worktree created")

// Single field
output.WithField("port", 8080).Info("service started")

// Chaining fields
output.WithField("service", "api").
    With("status", "running").
    Info("health check passed")
```

### Available Functions

- `output.Info(msg, args...)` - Info-level message (human mode only)
- `output.Debug(msg, args...)` - Debug-level message (verbose mode only)
- `output.Warn(msg, args...)` - Warning message (stderr; dropped by `-q`)
- `output.Error(msg, args...)` - Error message (stderr; printed in every mode)
- `output.Fatal(msg, args...)` - Fatal error and exit
- `output.Success(msg, args...)` - Success message

### Structured Logging Functions

- `output.WithField(key, value)` - Add a single field
- `output.WithFields(map[string]interface{})` - Add multiple fields
- `output.GetLogger()` - Get the underlying charmbracelet/log logger

## Examples

### Debug Logging

```bash
GIT_HOP_VERBOSE=1 git hop add feature-x   # or: git hop -V add feature-x
```

### JSON Output for CI/CD

```bash
git hop status --json | jq .
```

### Health Check for Scripts

doctor exits like `git fsck`: 0 when healthy (warnings alone do not
count), 1 when it reports an issue it did not fix:

```bash
if git hop --quiet doctor; then
    echo "Healthy"
else
    echo "Issues found"
fi
```

With `--fix` it exits 0 only if every issue was fixed, so
`git hop doctor --fix || echo "needs attention"` flags what repair could
not handle. The records (`--json`) still say which issue is which.

## Git-like Styling

git-hop maintains Git's minimal, professional aesthetic:

- Errors use `error:` prefix and go to stderr
- Fatal errors use `fatal:` prefix and exit with code 1
- Info messages have no prefix in human mode
- Debug messages use `debug:` prefix in verbose mode
- Colors are minimal and consistent with Git

## Best Practices

1. **Use Info for user-facing messages** in human mode
2. **Use Debug for diagnostic information** that helps troubleshoot issues
3. **Use Error for recoverable errors** that don't stop execution
4. **Use Fatal for unrecoverable errors** that require exit
5. **Use structured logging** when context is important (branch, repo, etc.)
6. **Respect the current mode** - don't output info in JSON/porcelain mode
