# Commands

git-hop provides a set of commands for managing hubs, hopspaces, and worktrees.

## git hop `&lt;uri&gt;`

Create a new hub and hopspace for a remote repository.

### Usage

```bash
git hop &lt;uri&gt; [flags]
```

### Examples

```bash tab="HTTPS"
git hop https://github.com/org/repo.git
```

```bash tab="SSH"
git hop git@github.com:org/repo.git
```

```bash tab="File Protocol"
git hop file:///path/to/local/repo
```

### What Happens

1. Detects server and organization
2. Clones the repository as a bare repository into the hub directory
   (`<repo>` in the current directory, or the path given)
3. Checks the default branch out at `hops/<default-branch>` in the hub
4. Writes the hub's `hop.json`: by default the hub is its own hopspace.
   With `--global` the hopspace is created under
   `$GIT_HOP_DATA_HOME/<org>/<repo>` (per `hop.dataLayout`) and the hub's
   `hop.json` is marked `repo.mode: global`
5. Points the hub's `current` symlink at the worktree
6. Sets up the worktree as add does: its ports and volumes,
   `.env` and, for a compose file with hardcoded host ports, the compose
   override, then shared dependencies. This happens before the
   `post-worktree-add` and `post-clone` hooks, so both see them. A set-up
   failure is reported; the clone still succeeds
7. After `post-clone`, starts the new worktree's environment only when
   asked: `--env-start`, `GIT_HOP_AUTO_ENV_START=true`, or
   `hop.env.autoStart` (default `false`). `--no-env-start` skips it for one
   clone. A failed start warns; the clone still succeeds. The start's
   output goes to stderr, as `git hop env start`'s does

### Output

Progress and next steps go to stderr, as `git clone`'s do:

```
Cloning git@github.com:org/repo.git...
Project root: /home/user/src/repo
Default branch: main
Creating bare repository...
Created local configuration (hub+hopspace) at /home/user/src/repo/hop.json
Successfully cloned to /home/user/src/repo
Project structure:
  /home/user/src/repo/  (bare repository)
    hop.json
    hops/
      main/  (worktree for current branch)
hint: You can now:
hint:   cd /home/user/src/repo/hops/main  # Work on current branch
...
```

## git hop add

Inside a hub: create a worktree (and branch, if needed) for a branch.
Aliases: `create`, `new`.

The new worktree starts clean: `git worktree add` runs in the hub's
repository, not in another worktree, so it does not copy that worktree's
sparse checkout or `config.worktree` keys (git copies them from the
worktree it runs in). A `--from` that only means something in a worktree,
such as `HEAD`, still names that worktree's commit.

### Usage

```bash
git hop add &lt;branch&gt; [flags]
git hop add [&lt;branch&gt;] --task &lt;id&gt; [flags]
```

### Flags

| Flag | Description |
|------|-------------|
| `--from <ref>` | Start-point for a new branch: branch name, ref, SHA, or `initial` for the root commit. Defaults to the tip of the repo's default branch (or `hop.add.defaultStartPoint`). If the branch already exists locally, an explicit `--from` fast-forwards it to `<ref>` (setting the upstream when `<ref>` is a remote-tracking branch) and refuses when the local branch is ahead of or has diverged from `<ref>`; without `--from` the existing branch is used as-is. |
| `--copy-ignored` / `--no-copy-ignored` | Copy the git-ignored local files from the fork-source worktree into the new one. Default follows `hop.add.copyIgnored` (`true`). |
| `--task <id>` | Record a task id for the worktree as `branches.<branch>.task` in `hop.json`, export it to the add hooks as `GIT_HOP_TASK`, and include it as `task` in the `--format json` result. Metadata only: the id is never part of the branch name. Without `<branch>`, the branch is derived as `<type>/<slug>` from the task (see [Branch from a task](#branch-from-a-task)). |
| `--env-start` / `--no-env-start` | Start the new worktree's environment once it exists, through the same code as `git hop env start`. Default follows `GIT_HOP_AUTO_ENV_START`, then `hop.env.autoStart` (`false`). Skipped silently when the worktree has no environment; a failed start prints a warning and a hint, and add still exits 0. The start's output goes to stderr, as `git hop env start`'s does. |
| `--fetch` / `--no-fetch` | Run `git fetch origin` before resolving the start-point, or skip it. Default follows `hop.add.fetch`; unset, add fetches only when the start-point is an origin ref (the default branch or an explicit `origin/<branch>`). A requested fetch that fails is fatal; the automatic one only warns. |
| `--dry-run` | Preview the branch, start-point, worktree path, task, hooks and environment start without writing anything or running any hook. An add the real run would refuse (the worktree exists, a file or non-empty directory is in its way, the branch name is invalid or checked out in another worktree, the start-point is not a commit, `--from` cannot move the existing branch) fails with exit status 1 and `[dry-run] would refuse to add '<branch>': <reason>` on stderr, the reason the real run gives. |

### Examples

```bash
git hop add feature-x
```

```bash tab="From a Tag"
git hop add hotfix-1 --from v2.3.0
```

```bash tab="Clean Worktree"
git hop add feature-x --no-copy-ignored
```

```bash tab="For a Task"
git hop add feat/login-redirect --task T-42   # explicit branch, task recorded
git hop add --task T-42                       # branch derived from the task
```

### What Happens

1. Validates current directory is a hub
2. Creates the branch from the start-point if it does not exist; a branch
   that exists only as `origin/<branch>` is created from it and tracks it
3. Creates the worktree at `hops/&lt;branch&gt;`. Nothing already there is
   deleted: a file or a non-empty directory at that path is refused
   (exit status 1), and an empty directory is reused, as
   `git worktree add` does
4. Copies git-ignored local files from the fork-source worktree (see below)
5. Generates the worktree's ports and volumes and links shared dependencies,
   before the `post-worktree-add` hook, so the hook finds `.env`, the
   compose override and the deps (see [Add hooks](./hooks#add-hooks))
6. Points the `current` symlink at the new worktree
7. Starts the environment, when asked (`--env-start` or `hop.env.autoStart`)
   and the worktree has one

### Branch from a task

`git hop add --task <id>` with no `<branch>` names the branch
`<type>/<slug>`:

- **type** comes from the task's first `type:<x>` tag that maps to a
  Conventional Commits type (`feat`, `fix`, `docs`, `style`, `refactor`,
  `perf`, `test`, `build`, `ci`, `chore`, `revert`; aliases such as
  `bug` → `fix` and `feature` → `feat`). Defaults to `feat`.
- **slug** is the task title in lowercase ASCII words joined by hyphens,
  at most 48 characters, cut on a word boundary.

The task is looked up with [tlc](https://github.com/hop-top/tlc):
`tlc task show <id> --format json`, run from the current directory with a
5-second timeout. When tlc is not on `PATH` or the lookup fails, add stops
and asks for the branch name: `git hop add <branch> --task <id>`.

If the branch already exists on `origin` but not locally (a collaborator
joining a task someone else started), it is checked out tracking
`origin/<branch>` rather than created fresh. This uses the remote-tracking
refs already present; run `git fetch` first to see new remote branches.

### Ignored Files

A fresh checkout has none of the ignored local state you depend on —
`.env`, editor and tool settings, small caches. `git hop add` copies
those from the worktree it forks from, never overwriting, skipping
dependency directories, and skipping any entry over
`hop.add.copyIgnoredMaxSize` (default `10m`). Every skip is reported.

Some ignored paths belong to one worktree only. Put `#-hop-#` on a
comment line directly above the pattern and everything that pattern
ignores stays behind:

```gitignore
# task-tracker state, one per checkout
#-hop-#
.tlc/
```

The marker works in any ignore file git consults (root or nested
`.gitignore`, `.git/info/exclude`, the global excludes file). It must be
on its own comment line: git reads a mid-line `#` as part of the pattern.
Details in [Configuration](configuration.md#hopaddcopyignored).

### Output

```
Created hopspace for 'feature-x'
Copied 4 ignored entries from /path/to/hub/hops/main
Setting up dependencies...
Worktree: ./hops/feature-x
```

## git hop `&lt;branch&gt;`

Inside a hub: switch to an existing worktree. Creates nothing; use
[`git hop add`](#git-hop-add) for a new one.

### Usage

```bash
git hop [-n] &lt;branch&gt;
```

`&lt;branch&gt;` must be a branch registered in the hub's `hop.json` (a row
of `git hop list`). A registered name always wins, even one shaped like an
`org/repo` clone shorthand (`feature/login`).

### Examples

```bash
git hop feature-x
```

```bash tab="Preview"
git hop -n feature-x
```

### What Happens

1. Finds the hub above the current directory
2. Runs the `pre-worktree-switch` hook; a non-zero exit aborts the switch
3. Points the hub's [`current` symlink](./current-symlink) at the worktree
4. Runs the `post-worktree-switch` hook; a failure only warns
5. Prints the worktree path

The binary cannot change its parent shell's directory. The
[shell integration](./shell-integration) wrapper does: after a
successful switch it `cd`s into the worktree `current` points at.
Without it, `cd` there yourself.

Ports, volumes and the environment are left as they are; start it with
`git hop env start`.

`-n`, `--dry-run` names the hooks that would run and the `current` target,
then stops: no hook runs and `current` is not written.

### Output

```
Switched to worktree 'feature-x'
Path: /path/to/hub/hops/feature-x
```

### Exit status

| Code | Meaning |
|------|---------|
| 0 | Switched |
| 1 | Branch not registered in the hub (`fatal: Worktree '<branch>' does not exist. Use 'git hop add <branch>' to create it.`), not in a hub, or `pre-worktree-switch` aborted |
| 93 | Switched, and `post-worktree-switch` reported that it navigated itself; the shell wrapper treats it as 0 and skips its `cd`. See [the navigation-handled directive](./hooks#the-navigation-handled-directive-exit-93) |
| 129 | Usage error (unknown flag) |

## git hop

With no arguments, prints help, as `git hop --help` does, and exits 0.
To see the worktrees, use [`git hop list`](#git-hop-list).

Help lists the daily commands. The ones that diagnose and repair hubs and
state, [`doctor`](#git-hop-doctor), [`repair`](#git-hop-repair) and
[`prune`](#git-hop-prune), form the MANAGEMENT group: `git hop --help-all`
lists them too, and `git hop --help-management` (or
`git hop help management`) lists them alone. They run and complete like
any other command.

### Usage

```bash
git hop [flags]
```

## git hop list

List the worktrees git-hop tracks: the current repository's inside a hub,
every tracked repository's outside one. Aliases: `ls`, `all`.

### Usage

```bash
git hop list [flags]
```

Each row carries the branch, its base, the worktree type, path, state
(`active` or `missing`) and the sync status `git hop status` reports.
For machine-readable output use `--json`, `--format` or `--porcelain`;
see [Structured Output](./09-reference#list).

## git hop status

Show detailed environment state for current worktree or hub.

### Usage

```bash
git hop status [target] [flags]
```

With a `target`, shows that worktree's state instead of the current one
(inside a hub only). `--all` shows every tracked repository, its
worktrees, configuration and resource use, and works outside a hub.
Aliases: `st`, `info`.

### Examples

```bash
git hop status
git hop status feature-x
```

### Output (worktree)

```
On branch feature-x
nothing to commit, working tree clean

Services:
  api    running  http://localhost:11500
  db     running  postgresql://localhost:11501
  cache  running  redis://localhost:11502
```

### Output (hub)

When run from a hub, the table includes a `Status` column reporting
each worktree's position relative to the hub's default branch.

```
Hub: org/repo
Location: /Users/jadb/.w/git
╭──────────────┬─────────┬───────────────────────────────┬──────────────╮
│ BRANCH       │ STATE   │ STATUS                        │ PATH         │
├──────────────┼─────────┼───────────────────────────────┼──────────────┤
│ main         │ Linked  │ default                       │ hops/main    │
│ feat/clean   │ Linked  │ synced                        │ hops/clean   │
│ feat/done    │ Linked  │ merged (4 behind)             │ hops/done    │
│ feat/wip     │ Linked  │ 3 ahead                       │ hops/wip     │
│ feat/old     │ Linked  │ diverged (1 ahead, 12 behind) │ hops/old     │
│ feat/gone    │ Missing │ -                             │ hops/gone    │
╰──────────────┴─────────┴───────────────────────────────┴──────────────╯
```

Status values:

| Value | Meaning |
|-------|---------|
| `default` | This is the hub's default branch |
| `synced` | Same tip as default — no commits ahead or behind |
| `merged` | Branch content is already in default (squash or rebase merge), or every branch commit has a patch-equivalent commit there (`git cherry` shows only `-`), and default has not moved on |
| `merged (N behind)` | Branch tip is reachable from default, or its content or every one of its commits is already in default (squash and rebase merges); default has moved on by N commits |
| `behind (N)` | Default has moved on by N commits and the branch has none of its own |
| `N ahead` | Branch has N commits not yet on default |
| `diverged (N ahead, M behind)` | Branch and default have both moved |
| `unknown` | Couldn't compute (e.g. default branch ref missing locally) |
| `-` | Worktree directory is not on disk (state `Missing` or `Occupied`) |

A `Missing` row means `hop.json` still lists a branch whose worktree
directory is gone. Run [`git hop prune`](#git-hop-prune) to drop those
rows.

An `Occupied` row means something other than a directory sits at the
worktree's path: a regular file, a symlink to one, or a dangling symlink.
It is not the worktree, and git cannot check the branch out over it;
[`git hop doctor`](#git-hop-doctor) reports it and leaves it alone. Move
it aside, then run `git hop doctor --fix` to recreate the worktree. The
`state` field of `--format json` and `status --all` use the same three
values: `Linked`, `Occupied`, `Missing`.

### Outside a hub

When no `hop.json` is found above the current directory, `status` looks
for a git-hop hub that is only missing its `hop.json`, and if it finds
one, says so and suggests `git hop init` there. A directory counts when
git reports it as a bare repository (`git rev-parse
--is-bare-repository`, so `core.bare` may be spelled any way git accepts,
set through an include, or kept in `config.worktree`) and `git worktree
list` shows at least one of its worktrees under `hops/`.

## git hop env

Control environment services.

### Usage

```bash
git hop env &lt;subcommand&gt; [flags]
```

### Subcommands

#### start

Start services for current worktree.

```bash
git hop env start
```

Output (all of it on stderr: it is progress, so stdout stays empty in
the human view; `--json`, `--format` and `--porcelain` put start's
[result](./09-reference#env-start-env-stop) there and nothing else):

```
Environment Manager: docker-compose
Ensuring dependencies...
Dependencies ready.
  Starting services: docker-compose
  Environment started successfully
```

The manager's hook output and the lifecycle command's own output (for
example `docker compose up -d`) go to stderr as well. The automatic start
after `add` and `clone` prints the same lines on stderr, beside their
result on stdout.

The status and step lines above are progress for a person at a terminal:
`-q`, `--json` and `--porcelain` drop them. Errors are always printed.

Under `-q`, the hook output and the lifecycle command's own output are
held back: dropped when the start or stop succeeds, printed on stderr
before the error when it fails. A failed automatic start after `add` or
`clone` is never silent either: its warning prints under `-q`, and the
command still exits 0.

#### stop

Stop services for current worktree.

```bash
git hop env stop
```

Output (on stderr, like `start`'s):

```
Environment Manager: docker-compose
  Stopping services: docker-compose
  Environment stopped successfully
```

#### generate

Write the current worktree's environment files (`.env` and, for a
compose file with hardcoded host ports, the compose override) without
starting anything. A worktree with no Docker environment is skipped.

```bash
git hop env generate
```

#### gc

Garbage collect orphaned dependencies. Aliased as `cleanup` and
`clean`, so `git hop env gc`, `git hop env cleanup`, and
`git hop env clean` are the same command.

```bash
git hop env gc [flags]
```

**Flags:**
- `--dry-run` - Preview what will be deleted without actually deleting
- `--no-prompt` - Skip the confirmation prompt (non-interactive callers)
- `--force` - Skip confirmation prompt (equivalent to `--no-prompt`)

**What it does:**
- Scans all worktrees to identify orphaned dependencies
- Shows dependency info including last used time and size
- Also lists the cached compose overrides
  (`$XDG_CACHE_HOME/git-hop/<org>/<repo>/...`) that no worktree of any hub
  git-hop records uses, and removes them with the rest: only the override
  and its metadata file are deleted, then the directories left empty
- Prompts for confirmation before deletion (unless `--no-prompt` / `--force`)
- Reports total space reclaimed

**Non-interactive runs:** piping an answer works — `echo y | git hop env
gc` proceeds, `echo n |` cancels. But if the prompt is reached with
nothing readable on stdin, `env gc` exits `129` with a `fatal:` message
on stderr telling you to pass `--no-prompt`. It never prints a quiet
`Cancelled.` and exits `0`, which a batch script would misread as a
successful collection.

> **Note on `cleanup` / `clean`:** `git hop cleanup` (top-level)
> resolves to [`git hop prune`](#git-hop-prune), while
> `git hop env cleanup` (under `env`) resolves to `git hop env gc`.
> They sit at different levels of the command tree and do different
> things — prune cleans state entries and aged-out backups, env gc
> reclaims unused dependency directories.

**Output:**

```
Running dependency audit...
  ✓ Scanned 3 worktrees
  ✓ Updated dependency registry

Orphaned dependencies:
  node_modules.def456  (last used: 7 days ago)  ~120MB
  venv.jkl012         (last used: 2 days ago)   ~45MB

Total reclaimable: 165MB

Delete these dependencies? [y/N]: y
  ✓ Deleted 2 orphaned dependencies
  ✓ Reclaimed 165MB
```

## git hop remove

Remove a hub, hopspace, or branch.

### Usage

```bash
git hop remove &lt;target&gt; [flags]
```

### Examples

```bash tab="Remove Branch"
git hop remove feature-x
```

```bash tab="Remove Hub"
cd ..
git hop remove my-project
```

```bash tab="Remove Hub and Its Volume Data"
cd ..
git hop remove my-project --delete-volumes
```

```bash tab="Unmerged Branch"
git hop remove feature-x --force
```

```bash tab="Dirty Worktree"
git hop remove feature-x --no-verify
```

### Safety Gate

`remove` probes the worktree before deleting and requires explicit
flags when the operation would lose work. A clean, merged branch
removes silently — no prompt, no warning. "Merged" covers merge
commits as well as squash- and rebase-merges, so a shipped branch never
needs a bypass flag just because its commits were rewritten on the way
in. A rewritten merge is detected by content (merging the branch would
not change default) or by patch-id (`git cherry <default> <branch>`
lists no `+` commit), which still holds once later commits on default
changed the same lines again. `status` and `remove --merged` use the
same test.

| Branch state | Required flags |
|--------------|----------------|
| Merged into default, clean | (none — silent pass) |
| Merged into default, dirty (uncommitted or untracked) | `--no-verify` |
| Not merged, pushed to `origin/<branch>`, clean | `--force` |
| Not merged, pushed to `origin/<branch>`, dirty (uncommitted or untracked) | `--force --no-verify` |
| Not merged and not pushed | `--force --no-verify` |

The dirty check applies whether or not the branch is merged. Pushing
protects a branch's commits, not the uncommitted or untracked files in
its worktree, so `--force` alone never discards them.

With `hop.gitflow.enabled`, a branch whose prefix matches a git-flow
type is finished (`git flow <type> finish`) before its worktree is
removed, which merges it into the type's parent. For such a branch:

| Branch state (git flow finish runs) | Required flags |
|--------------|----------------|
| Clean, merged or not, pushed or not | (none — silent pass) |
| Dirty (uncommitted or untracked) | refused, whatever the flags |

Unpushed commits need no `--no-verify`: the merge keeps them on the
parent. A dirty worktree is refused because finish runs in it and the
removal would then discard the changes; commit or stash them, or
remove the branch unfinished with
`git -c hop.gitflow.enabled=false hop remove <branch> --force --no-verify`.
If finish fails, nothing is removed.

When the gate is not satisfied, `remove` exits with status 1 and
prints which flag(s) to add. The gate cannot be bypassed any other
way.

Any branch that trips the gate also triggers the confirmation prompt
that runs immediately after it, so each gate message also names
`--no-prompt` for non-interactive callers. Following the printed hint
verbatim succeeds on the first retry.

### `--force` vs `--no-verify` vs `--no-prompt`

These three flags do **different** things. They are not interchangeable.

| Flag | Purpose | Bypasses gate? |
|------|---------|----------------|
| `--force` | Allow removing a branch that is **not merged** into the default branch | Yes — for the unmerged case only; **never** for a dirty worktree |
| `--no-verify` | Allow removing a worktree with **uncommitted/untracked files** (merged or not) or **unpushed commits** | Yes — for the dirty/unpushed case only; **never** for the unmerged case |
| `--no-prompt` | Skip the post-gate "Really delete?" confirmation. Useful in scripts | **No** — never bypasses the gate |

`--force` and `--no-verify` are independent: neither implies the
other. An unmerged branch is refused with `--no-verify` alone, and a
dirty worktree is refused with `--force` alone, merged or not.
Despite the name, `--no-verify` does not skip the
`pre-worktree-remove` / `post-worktree-remove` hooks; they always run.

In particular, `--no-prompt` alone on a risky removal will **fail
fast with exit 1**, not silently delete. You must combine it with
the appropriate `--force` / `--no-verify` to actually remove. Example:

```bash
# Branch is unmerged + dirty + unpushed, automated cleanup:
git hop remove feature-x --force --no-verify --no-prompt

# Just --no-prompt on the same branch → exit 1 with gate error.
git hop remove feature-x --no-prompt   # ✗ refuses
```

For hub removal, only `--no-prompt` matters (there is no gate; the
prompt is the only confirmation). The prompt says whether the hub's
volume data is kept or, with `--delete-volumes`, deleted.

### Non-interactive runs

The confirmation prompt reads stdin. When it cannot be answered —
a non-interactive shell with nothing piped in — `remove` exits **129**
with a `fatal:` message on stderr telling you to pass `--no-prompt`.
It does **not** print `Cancelled.` and exit 0, which would let a batch
script mistake a skipped removal for a completed one.

Piping an answer works as expected, so `yes | git hop remove …` and
`echo n | git hop remove …` both behave like a typed reply. A typed
`n` remains a normal cancellation: `Cancelled.` on stdout, exit 0.

### What Gets Removed

- Worktree (its directory, through `git worktree remove`)
- Local branch
- Its records: the hub's and the hopspace's `hop.json` entries and its
  state entry
- Its port and volume allocations: its `ports.json` and `volumes.json`
  entries, so the ports are free for another worktree

What stays:

- Volume data: the volume directories, and the data in them, stay;
  removing a branch drops its entry from `volumes.json` only. See
  [Volume data](#volume-data) for removing a hub.
- The Docker environment: `remove` never stops or removes containers,
  networks or Docker volumes. A container still running keeps the ports
  `remove` has just freed, which the next allocation may hand to another
  worktree. Run [`git hop env stop`](#stop) in the worktree before
  removing it (once it is gone, `env stop` cannot find it). That runs
  `docker compose stop`: the containers stop but stay, with their
  network. To remove them as well, run `docker compose -p <project> down`
  there, `<project>` being the `project` of the worktree's `ports.json`
  entry ([Ports Configuration](./configuration.md#ports-configuration));
  `git hop env down` is `env stop` under another name and does not.

The branch on `origin` is **not** touched. Removal is a local
operation and never contacts the network unless you ask it to.

Only `git worktree remove` deletes the worktree's files. When git
refuses (a locked worktree, a permission error), or the recorded
directory is not a worktree git has registered and is not empty, remove
fails with exit status 1 and leaves the files, the `hop.json` entry and
the branch as they were. An unregistered directory that is empty, or
already gone, is removed as before.

### Removing a hub

`git hop remove <hub-path>` deletes the hub's worktrees, the hub
directory and the hub's state entry; the repository's other hubs stay
in state. `--dry-run` lists each of these. A default hub keeps its hopspace in itself, so that goes with
it. A `--global` hub's hopspace lives in
`$GIT_HOP_DATA_HOME/<org>/<repo>` and may be shared by other hubs of
the same repository, so it is deleted only when no other hub state
records still uses it: one whose `hop.json` marks it global
(`repo.mode: global`) and so resolves to that hopspace. Otherwise it is
kept, with a `hint:`, and goes with the last hub that uses it. A kept
hopspace loses the removed hub's entries: its worktrees' records in
`hop.json` and their ports and volumes.

- A hub state records whose directory is gone does not count as using
  it.
- A hub whose `hop.json` cannot be read counts when state recorded it
  as global, so a hub that may still be repaired keeps its hopspace.
- When state itself cannot be read, which hubs use the hopspace is
  unknown and it is kept.

`--dry-run` says whether the hopspace would be kept or deleted, and
why, and how many of the hub's `hop.json` records a kept one would lose.

Removing a hub does not stop its worktrees' environments either: run
`git hop env stop` in each worktree with a running environment first
(see [What Gets Removed](#what-gets-removed)).

### Volume data

Removing a hub never deletes volume data unless you ask. The volume
directories in the hub (`volumes/`, plus any `basePath` or directory its
`volumes.json` records inside the hub), and those of a `--global`
hopspace removed with it, are moved aside before anything is deleted, to

```text
$GIT_HOP_DATA_HOME/orphaned-volumes/<org>/<repo>/<hub-key>-<UTC>/   # the hub's
$GIT_HOP_DATA_HOME/orphaned-volumes/<org>/<repo>/hopspace-<UTC>/    # the hopspace's
```

keeping each directory's path, so `volumes/hop_main_db` lands in
`<...>-<UTC>/volumes/hop_main_db`. `<UTC>` is the second of the removal
(`20260925T120000Z`); a directory already there is never reused or
overwritten (`-1`, `-2`, ... follow). The hub directory then goes
entirely, so a later `git hop clone` into the same path works, and a
re-created hub starts with empty volumes instead of silently picking up
the old data. A `hint:` names where the data is; delete it by hand once
it is no longer needed. A directory that holds nothing is not volume
data and goes with the hub.

The move is a rename. When that fails (the data home is on another
filesystem), the data stays where it was, with a `warning:`, and so does
the directory leading to it: the hub directory then holds only
`volumes/`. Nothing is copied.

A hopspace other hubs keep stays, and the removed hub's volumes in it
(`volumes/<hub-key>/`) stay with it.

`--delete-volumes` deletes all of that volume data with the hub instead,
after the same confirmation as the removal itself. It applies only to
removing a hub; with a branch or `--merged` it is a usage error (exit
129). `--dry-run` says which it would do, and the result's `hub` and
`hopspace` records say `volumes: kept` or `volumes: deleted` and where
(`volume_paths`).

Docker named volumes are Docker's: `git hop` never runs
`docker compose down -v` or `docker volume rm`, so they survive every
removal, with or without `--delete-volumes`. `git hop env stop` runs
`docker compose stop`.

### `--delete-remote`

Also delete the branch on `origin`, after the local removal:

```bash
git hop remove feature-x --delete-remote
```

Without this flag `remove` issues no network calls at all, so an
unreachable, slow, or credential-gated origin cannot stall the
command. With it, the `ls-remote` probe and the delete push run under
[`hop.remote.timeout`](./configuration.md#hopremotetimeout) and fail
with a stated cause rather than hanging.

Repair backups (the `repair-*` snapshots described under
[`git hop repair`](#where-repair-keeps-its-state)) for the removed
worktree are **not** auto-deleted. Run `git hop prune` to clean those up once the
retention window has passed; see
[`hop.repair.backupRetention`](./configuration.md#hoprepairbackupretention).

### `--merged`

Remove every worktree whose branch is merged into the hub's default
branch in one pass. Useful after a sprint of squash-merged PRs.

```bash
git hop remove --merged
```

```bash tab="Non-interactive"
git hop remove --merged --no-prompt
```

`--merged` skips the default branch itself and the worktree you are
currently in. Each candidate still goes through the standard safety
gate: a merged branch with a clean tree removes silently, a dirty one
needs `--no-verify`, and so on. The persistent `--force` and
per-removal `--no-verify` / `--no-prompt` apply uniformly to every
candidate.

`--merged` and a positional `<target>` are mutually exclusive — pass
one or the other.

### `--dry-run`

Preview any removal (a branch, `--merged`, or a whole hub) without
changing anything:

```bash
git hop remove feature-x --dry-run
```

The preview runs the safety gate exactly as a real removal would and
prints its verdict. A removal the gate would refuse fails the same way,
with exit status 1, so a script can use `--dry-run` to ask "would this
go through?". So does one whose worktree the real run would not remove,
as far as that is known before git runs: a directory that is not a
worktree git has registered and is not empty, a worktree git has locked
(`git worktree unlock` it first), or one whose `.git` file is missing.
A permission or I/O error git would hit deleting the files cannot be
known in advance. Uncommitted or untracked files are the safety gate's
business, not git's: `--no-verify` lets the removal delete them.
With `--merged`, each such candidate is skipped, with the reason, and
the preview exits 1 as the real run does.
Otherwise it lists the hooks that would run, the worktree
and branch that would be deleted, and the hop.json, hopspace and state
entries that would be dropped. No hook runs, the remote is never
contacted (even with `--delete-remote`), and no prompt is shown.

## git hop prune

Remove orphan state entries and aged-out repair, conversion and state
backups. Aliased as
`cleanup` and `clean` — `git hop prune`, `git hop cleanup`, and
`git hop clean` are the same command.

### Usage

```bash
git hop prune [flags]
```

### Examples

```bash
git hop prune
```

```bash tab="Dry Run"
git hop prune --dry-run
```

```bash tab="All Repositories"
git hop prune --all
```

```bash tab="Aliases"
git hop cleanup
git hop clean
```

### Flags

| Flag | Description |
|------|-------------|
| `--all` | Prune every repository in the state file, not just the current one |
| `-n`, `--dry-run` | Preview what would be pruned without applying (global flag) |

### Scope

By default `prune` only touches the **current repository** — the one whose
hub contains your working directory, resolved the same way
[`git hop list`](#git-hop-list) resolves it. Entries belonging to other
registered repositories are left alone.

Pass `--all` to sweep every repository in the state file. Run outside any
known repository, `prune` exits with an error rather than defaulting to a
global sweep; pass `--all` there if a global sweep is what you want.

Every line naming a pruned entry is prefixed with the repository it belongs
to, so an `--all` run shows exactly which repositories it touched.

Scoping matters because the two halves of a prune are not equally
recoverable: `hop.json` rewrites are snapshotted and can be rolled back
with [`git hop repair --undo`](#git-hop-repair), but removals from the
state file cannot be undone from the CLI. A repo-local prune that reached
a sibling repository would silently drop its registration, surfacing later
as `repository not found`.

### What It Does

For the repositories in scope, `prune` cleans up seven classes of stale
data, and with `--all` two more:

- **Orphan worktrees** — state entries whose paths no longer exist on
  disk. Common when a worktree dir was `rm -rf`'d manually.
- **Orphan hubs** — hub entries whose directories are gone. Same idea
  one tier up.
- **Records of an orphan `--global` hub** — the entries the hopspace it
  shared with the repository's other `--global` hubs
  (`$GIT_HOP_DATA_HOME/<org>/<repo>`) keeps for its worktrees: their
  records in that hopspace's `hop.json` (dropped under its lock) and
  their `ports.json` and `volumes.json` entries, freeing the ports. Only
  the records go: the volume directories they name, and the data in
  them, are left alone. The other hubs' records stay.
- **Orphan `hop.json` entries** — branch rows in a hub's `hop.json`
  whose worktree directory is gone. These are the rows
  [`git hop status`](#git-hop-status) renders as `State: Missing`;
  pruning them is what clears the row from the table.
- **Repair backups older than retention** — `repair-*` snapshot
  directories created by `git hop repair`, older than
  `hop.repair.backupRetention` (default `720h` = 30 days), in the hub's
  repair state dir and in any legacy `<hub>/.hop/backups/`. See
  [git config Settings](./configuration.md#git-config-settings) for
  how to tune retention.
- **Conversion backups beyond retention** — the backups
  `git hop init` keeps (`--keep-backup`, `hop.backup.keepBackup`)
  under `hop.backup.path` and the default cache root: those beyond the
  newest `hop.backup.maxBackups` (default 3) of the repository, or
  older than `hop.backup.cleanupAgeDays` (default 30). Backups of
  failed conversions are never removed; prune names them in a `hint:`.
  See [Conversion backups](./configuration.md#conversion-backups-hopbackup).
- **State backups older than retention** (`--all` only) — the copies of
  `state.json` git-hop takes before migrating it to the current format
  (`$XDG_STATE_HOME/git-hop/backups/state-<timestamp>.json`, see
  [State Tracking](./configuration.md#state-tracking)), older than
  `hop.repair.backupRetention`. `0` or a negative value keeps them all.
  They belong to no one repository, so a prune scoped to one leaves them.
- **Temp files of interrupted saves** — a save of `hop.json` writes
  `hop-config-<digits>.tmp` beside it (as saves of `ports.json` and
  `volumes.json` do in the hopspace) and renames it into place; a run
  that dies in between leaves the temp file. Prune removes those at
  least an hour old next to the `hop.json` of each hub in scope and of
  its hopspace. With `--all` it does the same for `state.json`'s
  `state.json.<digits>.tmp` in `$XDG_STATE_HOME/git-hop`, which belong
  to no one repository. Only files named exactly so are touched. The
  sweep holds the file's lock; when a save holds it, prune warns and
  leaves the files for a later run.

Rewriting `hop.json` goes through the same backup mechanism
`git hop repair` uses: the pre-prune file is snapshotted to
`$XDG_STATE_HOME/git-hop/repair/<hub>/backups/repair-<timestamp>Z`
before any row is dropped, so a prune can be rolled back with
[`git hop repair --undo`](#git-hop-repair).

Prune also retires the `<hub>/.hop/` directory that releases before the
relocation created for the lock and backups. For every hub in scope it
moves surviving `.hop/backups/repair-*` snapshots to the state dir (they
keep their id, so `--undo <id>` still works), removes a `.hop/repair.lock`
no process holds, and removes `.hop/backups/` and then `.hop/` itself
when — and only when — they are empty. A `.hop/` holding anything else
(another tool's files) is left exactly as it is. Each step is reported on
stderr as a `hint:` line; under `--dry-run` the hints say what would
happen and nothing moves.

A worktree that git has locked (`git worktree lock`, for example one on
a drive that is not mounted) is left alone even when its directory is
missing, as `git worktree prune` does. Its state entry and `hop.json` row
stay, both with and without `--dry-run`. Prune prints a `Skipping ...:
locked in git: <reason>` line for each one, followed by a `hint:` that
names `git worktree unlock <path>`. In structured output these entries
have the action `skipped` and a `reason`. Once the worktree is unlocked,
the next prune removes the entries.

`prune` does **not** remove merged branches that still exist on disk —
for that, use [`git hop remove --merged`](#git-hop-remove). It also
does not touch containers, volume directories, or symlinks; those go through
[`git hop env gc`](#gc) and [`git hop doctor --fix`](#git-hop-doctor).

## git hop doctor

Check for inconsistencies and print diagnostics. Use `--fix` to automatically repair issues.

### Usage

```bash
git hop doctor [flags]
```

### Examples

```bash
git hop doctor
```

```bash tab="Auto-fix Issues"
git hop doctor --fix
```

```bash tab="Preview Repairs"
git hop doctor --fix --dry-run
```

### Flags

- `--fix` - Automatically repair detected issues
- `--dry-run` - With `--fix`, report every repair without applying any of it

### What It Checks

- Path configuration: the data directory. The config and cache
  directories are shown but optional: whatever writes to them creates
  them, and whatever reads them treats a missing one as empty
- Hub configuration and symlinks
- The current hub's origin fetch refspec: an origin with a URL but no
  `remote.origin.fetch`, as a plain `git clone --bare` leaves it, is an
  issue: `git fetch origin` then updates `FETCH_HEAD` only and
  `refs/remotes/origin/*` never moves. `--fix` leaves it; run
  [`git hop repair`](#git-hop-repair) to restore
  `+refs/heads/*:refs/remotes/origin/*`
- Hopspace consistency: the hub itself for a default clone, or
  `$GIT_HOP_DATA_HOME/<org>/<repo>` for a hub cloned with `--global`
  (marked `repo.mode: "global"` in its `hop.json`); a data-home copy next
  to an unmarked hub is reported as a warning and left alone
- Records in a `--global` hopspace of worktrees of a hub that no longer
  exists: state does not record it and its directory is gone (deleted by
  hand, then taken out of state by a `doctor --fix` or `prune` of an
  earlier release; both now drop them with the hub). Nothing reads
  them: a warning, and `--fix` drops them from the hopspace's `hop.json`
- Hopspaces of `--global` hubs left at the path another `hop.dataLayout`
  builds (`<org>/<repo>` after switching to `{host}/{org}/{repo}`, or the
  reverse), as the layout in effect for each hub resolves it: a warning.
  `--fix` renames the directory to the current location when nothing is
  there yet (`--fix --dry-run` previews the move), holding the hopspace's
  `hop.json` and `ports.json` locks, so it waits for a command changing
  them. With data at both locations, a worktree inside the old one or a
  worktree link into it (a deps store link), or hubs of the repository
  that resolve the layout differently, nothing is moved and the reason is
  named. Nothing is deleted or overwritten; emptied parent directories
  stay
- Hopspace hooks earlier releases mirrored to
  `$GIT_HOP_DATA_HOME/github.com/<org>/<repo>/hooks`, where they still
  fire: a warning. `--fix` moves the directory to the `hop.dataLayout`
  location (`$GIT_HOP_DATA_HOME/<org>/<repo>/hooks` by default) when
  nothing is there yet; with hooks at both locations nothing is moved and
  both are named. Nothing is deleted or overwritten
- An invalid `hop.dataLayout`, at `--global` or in effect for the current
  hub (its own config, `git -c`): a warning naming the scope; the
  `--global` value, or the default, is used
- Directories under the hopspace's `hops/` that `hop.json` does not
  record, each an issue. `--fix` removes only an empty one. A worktree
  git has registered (at the directory or below it) is never removed,
  whatever is in it: record it with [`git hop repair`](#git-hop-repair)
  (`git hop repair --force-dirty` when it has uncommitted changes, which
  repair otherwise refuses; the hint and the issue name the one to run)
  or remove it with `git worktree remove`. Any other directory with
  something in it is left for you to empty or delete; `--fix` cannot
  repair either
- Orphaned worktrees and hubs in state. `--fix` prunes a hub whose
  directory is gone; for a `--global` hub it also drops, in the same run,
  the hub's records in the hopspace it shared with the repository's other
  `--global` hubs, as [`git hop prune`](#git-hop-prune) does: the worktree
  records in its `hop.json` and the entries in its `ports.json` and
  `volumes.json` (`fixed` records under the `hopspace` check, subject the
  worktree path). The volume directories, and the data in them, stay
- A hub worktree registered in another repository than the hub's own:
  an issue `--fix` cannot repair. Earlier releases could register a
  `--global` hub's new worktree in another hub of the same repository.
  The hint says how to move it: commit its work, fetch its branch into
  the hub (`git -C <hub> fetch <repository> <branch>:<branch>`), remove
  the worktree from the other repository (`git -C <repository> worktree
  remove <path>`), then run `git hop doctor --fix` to recreate it in the
  hub
- A repository state still keys by another host than its origin's,
  because the `<host>/<org>/<repo>` key its origin gives was already
  taken when state was migrated: an issue (exit 1). Both entries are
  kept and `--fix` does not merge them; the hint says how to merge them
  by hand: copy `state.json`, move the named hubs and their worktrees
  into the entry under the new key, and delete the old entry
- The current hub's record in state: a hub with a `hop.json` that state
  does not record (converted by a release that did not record
  conversions), or records without some of its worktrees, is an issue:
  `git hop list`, `git hop status --all` and `git hop prune --all` read
  state and do not see it
- Dependency health (symlinks, shared storage, orphaned deps)
- Ports two worktrees hold, across every hub of every repository, each a
  warning (exit status unaffected) naming the worktree of the hub set up
  later. `--fix` leaves them: re-porting would break a running
  environment. Run `git hop env generate` in that worktree to give it new
  ports
- A `managers.json` that cannot be read or parsed. Every command skips it
  with a warning and keeps its `hop.*` git config settings, so its package
  and environment managers do not apply until it is fixed; an issue
  `--fix` cannot repair
- A `config.json` in the config directory (`$XDG_CONFIG_HOME/git-hop/`).
  git-hop does not read it: settings live in git config `hop.*`. Reported
  as a warning (exit status unaffected) with a hint that the file can be
  deleted; doctor never deletes it, `--fix` included
- A `hops.json` in the config directory: the hub registry earlier
  releases wrote on clone and init. git-hop no longer writes or reads it;
  state records every hub and worktree. Reported as a warning (exit
  status unaffected) with a hint that the file can be deleted by hand;
  doctor never deletes it, `--fix` included
- Leftovers of the old `global.json` migration: `--global` `hop.*` keys it
  wrote as `false`/`0`/`""` although `global.json` never set them. They
  shadow the defaults (`hop.worktreeLocation` `""` selects the centralized
  layout). Checked only when `hop.migrated` is `true` and
  `global.json.bak` still exists; a key counts only while it holds the
  value the migration wrote
- Retired settings in `git config --global` and in the current hub's own
  config, whatever their value, each reported as a warning (exit status
  unaffected): `hop.autoEnvStart` (the setting is now `hop.env.autoStart`),
  `hop.bareRepo`, `hop.showAllManagedRepos`, `hop.unusedThresholdDays`,
  `hop.conventionWarning`, `hop.enforceCleanForConversion`,
  `hop.conversion.enforceClean`, `hop.conversion.allowDirtyForce`,
  `hop.conversion.autoRollback`, `hop.backup.enabled` and
  `hop.backup.preserveStashes`. Nothing reads them, and earlier releases
  wrote several on their own. They are not counted as migration leftovers
- Temp files a save of `state.json`, or of the current hub's `hop.json`
  (and of its hopspace's, which `ports.json` and `volumes.json` share),
  left beside it when its run died before renaming them into place, once
  an hour old: `state.json.<digits>.tmp` and `hop-config-<digits>.tmp`.
  A warning (exit status unaffected); `--fix` removes them with the sweep
  [`git hop prune`](#git-hop-prune) uses
- The current hub's repository format: `extensions.worktreeConfig` on at
  `core.repositoryformatversion` 0, as conversions by earlier releases
  left it, is reported as a warning (exit status unaffected). git honours
  the extension at version 0; tools that read extensions only at version
  1 (libgit2, JGit) would miss the hub's per-worktree `core.bare`

### Exit status

Like `git fsck`: 0 when healthy or only warnings were found, 1 when an
issue was reported and not fixed. With `--fix`, 0 only if every issue was
fixed; `--fix --dry-run` exits 0 only if every issue would be. The report
is printed either way.

### Auto-fix

Not every issue has a repair: a `managers.json` that does not parse, a
state key collision, an origin without a fetch refspec (`git hop
repair` restores it), a directory under `hops/` that `hop.json` does
not record and that is not empty or is a registered worktree, or an unmerged branch's worktree path that
something else occupies are left for you, with an `error:` or `hint:`
saying what to do. The summary suggests `--fix` only when it can repair
at least one issue found, says how many when it can repair only some,
and otherwise points at the errors and hints. Each issue's `fixable` field in the structured result
says the same. With `--fix`, the summary says some issues could not be
fixed exactly when one is left.

When issues are found, use `--fix` to automatically repair them:

```bash
git hop doctor --fix
```

The `--fix` flag will:
- Create missing directories
- Recreate a `--global` hub's missing hopspace
- Unset the `global.json` migration leftovers from `git config --global`
  (only here; git-hop never does it on its own)
- Unset every retired setting (all values of it) from the scope that holds
  it, `--global` or the current hub's config, and no live key
- Set the current hub's `core.repositoryformatversion` to 1 when it has
  `extensions.worktreeConfig` on at version 0
- Remove empty directories under `hops/` that `hop.json` does not record
  (never one with anything in it)
- Remove the stale temp files interrupted saves left, unless a save
  holds the file's lock at the time (they stay for a later run)
- Register branches from hub to hopspace
- Record the current hub in state, with its worktrees whose directory
  exists, as `init` and `clone` record a new hub. This merges with what
  state holds and never overwrites it: another hub of the same repository
  is kept with its worktrees, including its own worktrees of the same
  branches, and so is every entry state already has. Running it again
  changes nothing. `git hop init` in a hub that already exists stays a
  no-op
- Sync hub-hopspace configurations
- Recreate or clean up worktrees missing on disk (see below)

#### Previewing repairs

Add `--dry-run` to see exactly what `--fix` would do without changing
anything:

```bash
git hop doctor --fix --dry-run
```

Every planned repair is printed with a `[dry-run] Would ...` prefix. No
directories are created, no worktrees recreated, no dependencies touched,
and neither `state.json` nor the hub's `hop.json` is rewritten — not even
the backup snapshot that a real `--fix` takes first, since writing a
backup is itself a change.

`--dry-run` on its own (without `--fix`) changes nothing either way: a
doctor run that is not repairing never mutates.

#### Worktrees missing on disk

When `--fix` finds a hub branch whose worktree directory is gone (for
example removed with `rm -rf`), it checks whether the branch is merged
into the hub's default branch. Squash- and rebase-merged branches count
as merged, by the same test `remove` and `status` use: the branch tip is
reachable from default, its content is already there, or every one of
its commits has a patch-equivalent commit there. A branch whose ref no
longer exists cannot be checked and counts as not merged.

- **Merged**: the worktree is not recreated. Doctor drops the branch's
  `hop.json` row and state entry without prompting. The reasoning: the
  worktree was already gone, the branch is already on default, so there's
  nothing left to lose. The branch itself is kept.
- **Not merged** (or the merge check fails), and always for the default
  branch itself: the worktree is recreated from the branch, so its
  commits are checked out again.

Either way, if git still registers the missing directory (it marks the
entry `prunable` in `git worktree list`), doctor first clears that
registration with `git worktree remove <path>`. That removes git's
bookkeeping for that one path only; it never runs for a directory that
exists, and leaves a locked worktree alone. `--dry-run` reports each of
these steps as `would-fix` without running them.

A missing worktree that git has locked (`git worktree lock`, for
example one on a drive that is not mounted) is not treated as broken.
Doctor reports it as a `warning`, not an issue, so it does not affect
the exit status. The warning includes git's lock reason when there is
one. Doctor does not recreate it, clear its registration, or drop its
state entry or `hop.json` row, with or without `--dry-run`. A `hint:`
names the command that releases it, `git worktree unlock <path>`. Once
it is unlocked, the next `--fix` treats it like any other missing
worktree.

A worktree path that something other than a directory occupies (a
file, a symlink to one, or a dangling symlink) does not count as the
worktree. The hub check reports it as an issue ("occupied by a
non-directory"), the state check and `git hop prune` treat the worktree
as missing, the dependency check skips it (with a note) and audits the
other worktrees, `git hop status` shows it as `Occupied`, and `--fix`
never checks a worktree out over it: the
recreate fails with the path named as in the way (below), and whatever
occupies it is left alone.

This applies **only** to worktrees that are missing on disk. Doctor
does not bulk-remove existing-but-merged worktrees — for that, use
[`git hop remove --merged`](#--merged).

Before recreating a worktree, doctor checks for the conditions that
make `git worktree add` refuse. These are: git still registers the path
and will not prune it (for example it is locked), the branch is checked
out in another worktree, something is in the way of the path (a file,
a dangling symlink, or a parent that is not a directory), or the branch
no longer exists, either locally or as `origin/<branch>`. If any of
these applies, the repair is reported as `failed` with the reason, and
`--dry-run` reports the same failure rather than a `would-fix`. The
preview and the real run always give the same verdict.

A worktree doctor cannot recreate keeps its `hop.json` row, since that
row may be the only record of an unmerged branch. If its state entry
remains, doctor prompts for one of: provide a new path, delete the
entry, or skip. Deleting or relocating the entry at the prompt also
releases the row.

## git hop repair

Safely repair stale worktree metadata (gitdir pointers, hop.json, git
registry) with backup + undo support. Follows git porcelain conventions:
mutates by default with safety nets; `-n`/`--dry-run` previews.

### Usage

```bash
git hop repair [flags] [-- <pathspec>...]
```

### Examples

```bash tab="Preview"
git hop repair -n
```

```bash tab="Apply with backup (default)"
git hop repair
```

```bash tab="Restore from latest backup"
git hop repair --undo
```

```bash tab="Restore specific backup"
git hop repair --undo=repair-20260501T123045Z
```

```bash tab="List backups"
git hop repair --list-backups
```

```bash tab="Stable scripting output"
git hop repair -n --porcelain
```

### Flags

| Flag | Description |
|------|-------------|
| `-n`, `--dry-run` | Preview the plan without mutating state |
| `--porcelain` | Stable tab-separated output for scripts (also `--json` and `--format`: `json`, `yaml`, `csv`, `text`) |
| `--undo[=<id>]` | Restore from backup (most recent if no id). Refused with exit 129 under `--json`/`--format`/`--porcelain` |
| `--list-backups` | List available backups, one per line (id, timestamp, action count; tab-separated). Refused with exit 129 under `--json`/`--format`/`--porcelain` |
| `--no-backup` | Skip the safety backup (requires `--force`) |
| `--force-dirty` | Allow repair when worktrees have uncommitted changes |
| `--force` | Bypass safety checks (combined with `--no-backup`) |
| `--base` | Infer and record the base branch of `hop.json` entries that lack one (best-effort heuristic; preview with `-n`) |
| `--[no-]progress` | Progress on stderr while checking the worktrees to repair and applying the fixes, in git's `<step>: NN% (x/y)` form. By default shown only when stderr is a terminal, and never under `-q` or a structured format. `--progress` forces it on (even with `-q`), `--no-progress` off; the last one given wins |
| `--color[=<when>]` | Colour of the human output: `always` (also bare `--color`), `auto` (default: only on a terminal, off under `NO_COLOR`) or `never`. Any other value is refused with exit 129. The global `--no-color` wins over it |

### Where repair keeps its state

Repair writes nothing into the hub except the fixes themselves. Its lock
and its backups live in a per-hub directory under the XDG state home:

```
$XDG_STATE_HOME/git-hop/repair/<hub-basename>-<hash>/
    repair.lock                  held while a run is in progress, removed on exit
    backups/repair-<UTC-ts>Z/    one snapshot per mutating run
        manifest.json            hub path, actions, sha256 of every file below
        hop.json
        .git_worktrees/
        pointers/
```

`$XDG_STATE_HOME` defaults to `~/.local/state`. The directory is keyed by
the hub's path (its basename plus a short hash), not by repository,
because repair exists to fix a damaged `hop.json` — the file the
repository identity would have to be read from. `--list-backups` and
`--undo` resolve the same directory from the hub you run them in.

Releases before this layout wrote `<hub>/.hop/repair.lock` and
`<hub>/.hop/backups/`. Those snapshots are still read: `--list-backups`
shows them and `--undo <id>` restores them. Nothing is written there any
more, and [`git hop prune`](#git-hop-prune) moves the survivors out and
removes the leftover `.hop/` once it is empty.

### Pipeline

1. Acquire `repair.lock` in the repair state dir (refuses concurrent runs;
   the file is removed again when the run ends, success or failure)
2. Plan: classify each worktree against on-disk + git registry + hop.json
3. Dirty-check (refuses unless `--force-dirty`)
4. Print plan; exit if `-n`
5. Fire `pre-repair` hook
6. Snapshot to `<state-dir>/backups/repair-<UTC-timestamp>/`
7. Apply each action; verify post-state predicate
8. Re-plan; auto-restore from backup if new issues appeared
9. Record in `state.json` each worktree `hop.json` gained, as
   [`git hop add`](#git-hop-add) records one (keyed by path, with its
   branch and hub), so `list`, `status --all` and `doctor` see it; a
   `--global` hub's data-home hopspace records it too. A row dropped for
   a worktree gone from git and disk loses its state entry and hopspace
   record
10. Fire `post-repair` hook

### Porcelain v1 format

One tab-separated record per worktree:

```
<status>\t<worktree-path>\t<action>\t<old-value>\t<new-value>
```

`<status>` ∈ `ok | repaired`. `<action>` ∈ `noop | rewrite-gitdir | register | unregister | update-hopjson | record-base | restore-fetch-refspec`.
An `update-hopjson` record that adds a worktree git knows but `hop.json`
lacks carries, as `<new-value>`, the branch git has checked out there
(`git worktree list --porcelain`): the entry is recorded under that
branch, with the worktree's absolute path, whatever its directory is
called. A worktree on a detached HEAD has no branch to record; repair
leaves it out of `hop.json` with a warning.
`--json` and `--format json` / `--format yaml` carry the same records with the keys
`status`, `path`, `kind`, `old`, `new`, plus `reason`; see
[Structured Output](./09-reference#repair).

### Exit codes

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | Operation failure (dirty worktrees, apply failed, hook aborted) |
| 128 | Fatal (lock held, not in a hub) |
| 129 | Usage error (bad flag) |

### Configuration

Tunables read via `git config`:

- `hop.repair.backupRetention` — max age of `repair-*` snapshots before
  `git hop prune` removes them. Go duration syntax (`720h` = 30d default).

### Hooks

Mutating runs fire `pre-repair` (a non-zero exit aborts before any
mutation) and `post-repair` (informational; its exit status is ignored).

Both resolve through the standard three-level search — repo, hopspace,
then global — like every other hook. See [Hooks](./hooks) for the full
priority order.

Two details specific to repair. `GIT_HOP_WORKTREE_PATH` is the hub, not a
worktree, since a repair run spans every branch; `GIT_HOP_BRANCH` is
empty for the same reason. And `GIT_HOP_REPO_ID` is resolved at dispatch
time, so `pre-repair` sees the possibly-damaged config while
`post-repair` sees the repaired one — it is empty rather than partial
when the hub config cannot yield an org and repo, which is exactly the
state `pre-repair` exists to inspect.

## git hop init

Convert an existing repository to the hub + worktrees layout.

### Usage

```bash
git hop init [--no-prompt] [--regular] [-n|--dry-run] [--force] [--keep-backup]
git hop init --restore &lt;backup-path&gt; [--force]
```

Aliases: `setup`, `install`.

| Flag | Description |
|------|-------------|
| `--no-prompt` | Skip the menu and convert non-interactively (bare unless `--regular`). Without it, a run with nothing readable on stdin fails rather than waiting |
| `--regular` | Convert to a regular repo + worktrees instead of bare (with `--no-prompt`) |
| `-n`, `--dry-run` | Show the conversion steps without executing them |
| `--force` | Convert despite uncommitted changes (a backup is still taken); with `--restore`, move what occupies the original location aside (never deleted) |
| `--keep-backup` | Keep the conversion backup after success (default: `hop.backup.keepBackup`) |
| `--restore <path>` | Restore the conversion backup at `<path>` to the location it was taken from (manual rollback) |
| `--hooks <mode>` | Mirror committed `.git-hop/hooks/` into the hopspace: `symlink`, `copy`, `prompt` or `none` (overrides `--no-hooks`) |
| `--hooks-overwrite` | Overwrite a hopspace hook whose content differs (`symlink` and `copy` modes) |
| `--no-hooks` | Skip hooks: no `.git-hop/hooks/` directory, no lifecycle hook runs |
| `--enable-chdir` | Install the shell integration for automatic directory switching after hop commands |

Run in a hub (a bare repository, a regular repository with `hop.json`,
or one of their worktrees), `init` reports it as already initialized.
A bare repository git-hop did not create (made with `git clone --bare`,
say) has no `hop.json` yet: `init` writes one listing its worktrees and
records the hub in git-hop's state, as a conversion does. When origin
has no fetch refspec, which `git clone --bare` leaves out, `init` also
sets `remote.origin.fetch` to `+refs/heads/*:refs/remotes/origin/*`, as
a clone's hub has it, so the next `git fetch origin` fills
`refs/remotes/origin/*`. Otherwise it changes nothing. Any other repository is offered a conversion, including
a regular one with linked worktrees from `git worktree add`: git does
not consider it bare, so it is not a hub yet.

Run from a linked worktree of such a repository, `init` acts on the
repository itself, as git commands run from a linked worktree do: it
says so on stderr and offers that repository the conversion. It never
writes `hop.json` into the linked worktree, and does not mark the
repository as a hub without converting it.

Register as-is (menu option 3) changes nothing on disk: no `hop.json`,
no `hops/`. It records the repository in git-hop's state, the repository
root as its branch's worktree, so `git hop list`, `status --all` and
`prune --all` see it. Run from inside it, `list`, `status` and `prune`
(without `--all`) recognise it from that record, as they recognise a
hub by its `hop.json`. Commands that change a hub's worktrees (`add`,
`remove`, `move`, `merge`, `repair`, `env gc`) still need a `hop.json`.

A bare conversion carries the repository's linked worktrees (from `git
worktree add`) into the hub; see [Linked worktrees](#linked-worktrees).

A conversion then sets up its initial worktree (`hops/<branch>` for a
bare conversion, the repository root for `--regular`) as `add` does:
its ports and volumes, `.env` and, for a compose file with
hardcoded host ports, the compose override, then shared dependencies.
This happens before the `post-worktree-add` hook, so the hook finds them
(see [Init hooks](./hooks#init-hooks)). `--no-hooks` skips the hook, not
the set-up, and `--dry-run` lists the set-up as the plan's last step. A
set-up failure is reported; the conversion still succeeds. Register
as-is sets up nothing.

### What carries over

A regular conversion (`--regular`) keeps `.git` where it is, so its local
config is untouched.

A bare conversion (the default) clones the repository into a new bare
hub, and a clone copies no local config. `init` carries it over: every
entry of the repository's `.git/config` is written into the hub's
config, in the same order and with every value of a multi-valued key.
That covers `user.*`, `url.*.insteadOf`, `core.hooksPath`, `alias.*`,
`commit.gpgSign`, `hop.*` and the rest. Remotes, their refspecs and each
branch's upstream come across as they were, along with the
remote-tracking refs, so upstreams resolve without a fetch.

The keys left out describe the old layout or the old storage format:

| Key | Why it is left out |
|-----|--------------------|
| `core.bare` | The hub is bare; it keeps the clone's `true` (in its own `config.worktree` when `extensions.worktreeConfig` is on, see below). |
| `core.worktree` | Names the old working tree; hub worktrees live under `hops/`. |
| `core.repositoryformatversion` | The clone sets it to match its own storage, and `init` raises it to 1 when the hub gets `extensions.worktreeConfig`, see below. |
| `extensions.*` | Repository format declarations (`objectFormat`, `refStorage`, ...); the clone writes its own. `extensions.worktreeConfig=true` is the exception: it carries over, see below. |
| `include.path`, `includeIf.<cond>.path` with a relative path, or a `gitdir:./` condition | Resolved against the directory of the config file, which moves from `<repo>/.git/` to `<repo>/`. `init` prints a `warning:` for each; set it again with an absolute path. |

Includes with an absolute or `~/` path are carried over, as the
directives themselves: the included file is not copied in. Filesystem
settings git probes on its own (`core.fileMode`, `core.ignoreCase`,
`core.precomposeUnicode`, `core.symlinks`) carry over too; the hub sits on
the same filesystem, so they only differ from the clone's when you set
them yourself.

Per-worktree config (`extensions.worktreeConfig`, which `git
sparse-checkout` turns on) carries over exactly. The hub gets the
extension, and its `core.bare=true` moves from the shared config into the
hub's own `config.worktree`, as git requires: in the shared config it
would apply to every worktree and break them. Its
`core.repositoryformatversion` goes to 1, as git sets it when it turns
the extension on. The entries of
`.git/config.worktree` (such as `core.sparseCheckout` and
`core.sparseCheckoutCone`) go to the default worktree's own
`config.worktree`, the same exclusions applying, and its sparse checkout
is applied again, so the default worktree has the files it had before.
Without the extension, git does not read `.git/config.worktree`; if the
file exists it is left behind with a `warning:`.

A sparse checkout set up without `git sparse-checkout` (older git, or by
hand) keeps `core.sparseCheckout=true` in the shared `.git/config`, with
no `extensions.worktreeConfig`. In the hub's shared config it would
apply to every worktree, so a bare conversion treats it as the default
worktree's own, as `git sparse-checkout` does: `core.sparseCheckout`,
`core.sparseCheckoutCone` and `index.sparse` go to the default
worktree's `config.worktree`, the hub gets the extension with
`core.bare` moved as above, and the sparse checkout is applied again.
Worktrees added later are full checkouts.

`git hop init -n` lists the keys it would carry over and the ones it
would leave out, with the reason. It prints key names only, never
values, since those can hold credentials.

The rest of the old `.git` directory is carried over too, where it still
means something in a bare hub:

| In the old `.git` | After a bare conversion |
|-------------------|-------------------------|
| `info/exclude`, `info/attributes` and the other `info/` files | In the hub's `info/`, which applies to every worktree, so ignored files stay ignored. `info/refs` is left out; `git update-server-info` regenerates it. |
| `info/sparse-checkout` | In the default worktree's own git dir, where git reads it for that worktree. |
| `hooks/` | Your hooks move to the hub's `hooks/`, which every worktree runs. The `*.sample` files are the clone's. |
| `refs/notes`, `refs/replace`, `refs/stash` and other ref namespaces | Copied into the hub. Branches and tags come with the clone. `refs/bisect`, `refs/worktree`, `refs/rewritten` and `refs/prefetch` are left out. |
| `logs/` | Reflogs carry over, including every stash entry. The old `HEAD` reflog goes before the default worktree's own. A shallow repository keeps only its latest stash: its hub may lack the commits older reflog entries name. |
| `modules/` (submodule repositories) | Moved to the default worktree's own git dir (`<hub>/worktrees/<name>/modules/`), which is where git keeps a linked worktree's submodules. Each checked-out submodule is reconnected, so `git submodule status`, `update` and `git -C <path> log` work without cloning again. Nested submodules at any depth are reconnected the same way. Other worktrees start without submodules; run `git submodule update --init` in each one, as git requires for any linked worktree. |
| `rr-cache/`, `lfs/`, `description`, `branches/`, `remotes/` | Moved into the hub. |
| `worktrees/` (linked worktrees' admin directories) | Copied into the hub's `worktrees/` under the same names; see [Linked worktrees](#linked-worktrees). Entries git calls prunable (their directory is gone and they are not locked) are left behind, with a `warning:`. |

Nothing else is kept. The objects and the shallow boundary come with the
clone. The index is rebuilt in the default worktree with the same
staged changes (see below); editor scratch files are dropped. `init`
prints a `warning:` for each of these:

- `config.worktree` when `extensions.worktreeConfig` is off: git was
  not reading it, so it is not carried over.
- Any entry git-hop does not recognise.

### Linked worktrees

A bare conversion carries each linked worktree into the hub. git keeps
a linked worktree's state in its admin directory,
`.git/worktrees/<name>/`: HEAD and its reflog, the index, per-worktree
refs (`refs/worktree/`, `refs/bisect/`), the lock, `config.worktree`,
`info/sparse-checkout`, and the git directories of its submodules.
`init` copies each admin directory to the hub's `worktrees/<name>/`,
under the same name, and reconnects the worktree to it, so the worktree
keeps its branch, staged and unstaged changes, untracked files, lock,
per-worktree config and sparse patterns. Uncommitted changes in a linked
worktree need no `--force`: its files do not move.

Where each one ends up:

- Outside the repository: it stays where it is. `hop.json` lists it
  under its branch with its absolute path.
- Inside the repository's working tree (such as `.worktrees/<name>`,
  ignored or not): it moves to `hops/<branch>/`, or `hops/<name>/` when
  its HEAD is detached, as `git hop add` would have placed it, instead
  of ending up inside the default worktree. Directories left empty by
  the move are removed.
- Locked and absent (on a disk that is not mounted): it is carried as
  it is, with a `warning:`. Once it is back, run `git -C <hub> worktree
  repair` to reconnect it.

A worktree with a detached HEAD is carried but not listed in `hop.json`,
which lists worktrees by branch. `hop.json` and git-hop's state record
the carried worktrees, so `git hop list` shows them. `init` did not
create them, so it runs neither the environment set-up nor the
`post-worktree-add` hook for them; only for the default worktree.

`init` refuses, before it backs up or moves anything, when a linked
worktree cannot be carried: an operation is paused in it (see
[Operations in progress](#operations-in-progress)), git seems to be
running in it (its admin directory holds `index.lock`), its branch is
also checked out in another worktree (with `git worktree add -f`; a hub
has one worktree per branch), it lies inside `.git`, inside another
linked worktree, or at `<repo>.new` or `<repo>.old`, where the conversion
builds the hub, or its `hops/` destination is taken. Each reason is
printed as an `error:`. `--dry-run` lists what happens to each linked
worktree, and refuses the same way.

After the conversion, `init` checks that git, run in each carried
worktree, finds its admin directory in the hub. If one does not, the
conversion fails and rolls back: the repository is restored from the
backup and every linked worktree is reconnected to it.

### Uncommitted changes and `--force`

`init` refuses to convert a repository with uncommitted changes. With
`--force` it converts anyway (the backup is still taken) and carries
them into the default worktree as they were: `git status`, `git diff
--cached` and `git diff` show the same staged and unstaged changes
after the conversion as before. That covers files partially staged
with `git add -p`, staged additions, deletions, renames, mode changes
and binary files, intent-to-add files (`git add -N`), files deleted
without `git rm`, and untracked files.

Two things cannot be carried exactly, and `init` prints a `warning:`
for each while keeping the content in the worktree, unstaged:

- An unmerged path, such as a conflicted `git stash pop`: its content,
  conflict markers included, is kept, but not the conflict's stages.
- Staged changes the new index does not accept: the conversion goes
  ahead with all of them in the working tree, unstaged.

### Operations in progress

A merge, rebase, `git am`, cherry-pick, revert or bisect stopped midway
keeps its state in the old `.git` directory, tied to its layout, so a
bare conversion could not carry it. `init` refuses to convert while one
is in progress, even when the working tree is clean (a rebase at an
`edit` stop, a bisect), and before it backs up or moves anything. It
looks for the same markers git does: `MERGE_HEAD`, `rebase-merge/`,
`rebase-apply/`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `sequencer/`,
`BISECT_START` and `BISECT_LOG`. It looks in every linked worktree's
admin directory too; the refusal then names the worktree, and the hints
run in it:

```text
$ git hop init --no-prompt
hint: finish the rebase with 'git -C /src/feat rebase --continue' or abort it with 'git -C /src/feat rebase --abort'
hint: then run git hop init --no-prompt again
fatal: a rebase is in progress in the linked worktree /src/feat; converting would abandon it
```

```text
$ git hop init --no-prompt
hint: finish the merge with 'git merge --continue' or abort it with 'git merge --abort'
hint: then run git hop init again
fatal: a merge is in progress; converting would abandon it
```

The exit status is 1. `--force` does not override the refusal: it
consents to carrying uncommitted files, not to losing a paused
operation. `--dry-run` reports the same refusal. A regular conversion
(`--regular`) keeps `.git` in place, so the operation survives it and
`init` does not refuse, unless the operation has detached HEAD (a
rebase, a bisect that has checked out a commit): see below.

### Detached HEAD

`init` names what it creates after the current branch: the bare
layout's `hops/<branch>/` worktree, the regular layout's `hop.json`
entry for the repository root. With no branch checked out it refuses,
for every layout and for register-as-is, before it backs up or moves
anything:

```text
$ git hop init --no-prompt
hint: check out a branch first, or create one at this commit:
hint:   git switch <branch>
hint:   git switch -c <new-branch>
hint: then run git hop init again
fatal: HEAD is detached; git hop init names the hub's worktree after the current branch
```

The exit status is 1. `--force` does not override it, and `--dry-run`
reports the same refusal. When a paused operation detached HEAD (a
rebase, most often), the hint says how to finish or abort that
operation instead.

## git hop move

Rename a worktree and its branch. Aliases: `rename`, `mv`.

### Usage

```bash
git hop move [&lt;old-branch&gt;] &lt;new-branch&gt;
```

With one argument, renames the current worktree's branch. Runs the
`pre-worktree-move` and `post-worktree-move` hooks.

Like `add`, move refuses a destination that a file or a non-empty
directory occupies (exit status 1; `-n` says `[dry-run] would refuse to
move '<branch>'`): `git worktree move` would put the worktree inside the
directory. An empty directory is taken; the worktree lands at the path
itself.

## git hop merge

Merge a worktree's branch into a receiving branch, then remove the source
worktree and its local branch and point `current` at the receiving
branch's worktree.

### Usage

```bash
git hop merge [&lt;source-branch&gt;] &lt;into-branch&gt; [flags]
```

With one argument, the current branch is the source.

The source worktree is removed as [`git hop remove`](#git-hop-remove)
removes one: only through `git worktree remove`. When that cannot
happen, the merge stands, but merge fails with exit status 1 and the
worktree, its `hop.json` entry and its branch stay. `--dry-run` fails
the same way, with exit status 1, for a source worktree that
`git hop remove --dry-run` would refuse to remove (see
[`--dry-run`](#--dry-run) under `git hop remove`).

### Flags

| Flag | Description |
|------|-------------|
| `--no-ff` | Create a merge commit even when a fast-forward is possible |
| `--delete-remote` | Also delete the source branch on `origin`. Without it merge stays local and never contacts the network. Default follows `hop.merge.deleteRemote` |

## Structured Output

`add`, `status` (including `status <branch>` and `status --all`), `list`,
